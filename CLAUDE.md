# elektronik.kz — контекст для Claude Code

Интернет-магазин электроники (ТОО/ИП пользователя, направление среди нескольких параллельных бизнес-инициатив). Читай этот файл в начале любой новой сессии в этом репозитории — ниже сжатая история решений, которые не видны из одного только кода.

## Стек и статус

- **Django 6.1**, Python 3.13, SQLite для разработки.
- `config/` — настройки и urlconf проекта.
- Приложения: `shop` (Product/Category/Brand + каталог), `accounts` (кастомный User, адреса, личный кабинет), `cart` (корзина), `orders` (заказы).
- `manage.py check` и `migrate` проходят чисто. Базовый e-commerce-флоу (каталог → корзина → оформление заказа) проверен вручную в браузере 2026-08-25.

## Авторизация и личный кабинет (2026-08-25)

- Кастомная модель `accounts.User` (`AUTH_USER_MODEL`) — вход по **email или телефону**, без `username`. Телефон в формате `+7XXXXXXXXXX`, валидируется regex в `accounts/models.py`.
- Единое поле логина "email или телефон" (`accounts/forms.py: LoginForm`), формат определяется автоматически (`@` → email). Бэкенд аутентификации — `accounts.backends.EmailOrPhoneBackend`.
- **SMS/OTP-верификация телефона осознанно не делалась** — пока просто пароль. Если понадобится, это отдельная задача с выбором SMS-провайдера (для КZ, например Mobizon/SMSC).
- `accounts.Address` — адреса доставки пользователя, один может быть помечен `is_default`; используется для автозаполнения формы заказа.
- Корзина (`cart.Cart`/`CartItem`) — гостевая на сессии (`session_key`) для неавторизованных, привязывается к `user` после логина; слияние гостевой корзины в пользовательскую — сигнал `user_logged_in` в `cart/signals.py`.
- Заказ (`orders.Order`/`OrderItem`) — оформляется только авторизованным пользователем (`checkout` требует логин); при оформлении сохраняется снимок цены/названия товара (`price`, `product_name` в `OrderItem`), а не ссылка на текущую цену.
- Важный нюанс: `AUTH_USER_MODEL` подключали, когда БД уже существовала с дефолтным `auth.User` — пришлось снести `db.sqlite3` и миграции (в базе был только тестовый `admin`, реальных данных не было). Если ещё раз понадобится менять модель User — снова потребуется чистая пересборка миграций, это нельзя сделать data-migration'ом задним числом без боли.
- Тестовый суперпользователь для dev: `admin@example.com` / `admin` — только для локальной разработки, не для продакшена.

## Как дошли до этого стека (2026-08-24)

Проект был размазан по трём несинхронизированным местам:
1. **Этот репозиторий** — раньше содержал Laravel-скелет (2 коммита, включая случайно закоммиченную `vendor/`, 8244 файла). Полностью удалён и заменён на Django.
2. **Хостинг hoster.kz** (тот же провайдер, что у ecomeken.kz) — корень домена отдаёт 403 (заглушка с 2021 года), но по адресу `elektronik.kz/wordpress/` был рабочий демо-магазин на WordPress/WooCommerce с каталогом из 7 товаров. **Решение: отказаться от WordPress**, эта ветка больше не развивается.
3. **Google Drive**, папка `elektronik-kz` — содержит то, что в git не попало:
   - прайс-листы поставщиков (**FDCOM/Acer, Marvel**) — активно обновляются, это реальный источник товарного ассортимента, ещё не подключён к проекту;
   - файл учёта остатков;
   - старый `.env.example` с продакшн-конфигом (`APP_URL=https://elektronik.kz`, MySQL) — актуален только по домену/окружению, не по стеку (там был Laravel).

Итог: Python/Django выбран сознательно, чтобы не распыляться на два стека и не тратить время на PHP, который пользователь не использует в других проектах.
