## Баг найден пользователем на реальном файле: CSV в CP1251 (2026-09-14)

Пользователь попробовал импортировать настоящий CSV (не мой тестовый) —
`UnicodeDecodeError: 'utf-8' codec can't decode byte 0xd0` на шаге
`batch_map`. Причина: `bulk_import/services.py:parse_file` и
`products/catalog_import.py:_read_rows` читали CSV только как
`utf-8-sig`, а реальные прайс-листы поставщиков (выгрузки из 1С/Excel)
часто в **Windows-1251**, не UTF-8 — это ожидаемо для рынка СНГ/KZ, мои
тестовые файлы этого не покрывали, т.к. я сам их создавал в UTF-8.
- Фикс в обоих местах одинаковый: `_decode_csv()` — пробует
  `utf-8-sig → utf-8 → cp1251` по очереди, если все упали — `utf-8` с
  `errors='replace'` (не падает никогда, в худшем случае несколько
  нечитаемых символов). Добавлены тесты на cp1251-файл в оба приложения
  (`products/tests.py`, `bulk_import/tests.py`).
- **Урок**: тестовые фикстуры на латинице/самодельном UTF-8 не ловят
  кодировочные баги, которые вылезают только на реальных файлах
  пользователя — раз этот проект специально про импорт прайс-листов
  поставщиков (см. `import/` папку), кодировка CSV — известная зона
  риска, надо было предусмотреть сразу, а не ждать первого реального файла.
- .xlsx это не касается — openpyxl сам разбирает XML/бинарный формат,
  проблема только с CSV.

## Реализован bulk_import — модерируемый Excel-импорт каталога (2026-09-14)

План из записи «Дальше по плану» (ниже) реализован и протестирован.
**Новое приложение `bulk_import`**, смонтировано под `/seller/import/`.

- **Модели**: `ImportBatch` (seller, file, status, column_mapping JSON, reviewed_by/at, rejection_reason) и `ImportRow` (batch, row_number, raw_data JSON, product FK, error). Статусы батча: `uploaded → mapped → images_pending → pending_approval → approved/rejected`.
- **Флоу продавца** (`seller_required`, переиспользован декоратор из `products.seller_views`): загрузка файла → превью первых строк + сопоставление колонок (`bulk_import/forms.py:ColumnMappingForm` — динамическая форма, по одному select на колонку) → повторное чтение файла по маппингу в `ImportRow.raw_data` (JSON-превью) → подтверждение создаёт реальные `Product(is_active=False)` (архитектура подтверждена заранее, см. ниже по дате) → обязательная загрузка картинки к каждому товару (`Product.image`, кнопка отправки на модерацию появляется только когда `ImportBatch.all_images_uploaded` — property, проверяет что у всех товаров батча есть картинка) → статус `pending_approval`.
- **Флоу администратора** (`bulk_import.views.moderator_required`, на `User.can_bulk_import_catalog` — то же свойство, что и у существующего простого импорта в admin): список батчей на модерации → детали (товары с картинками) → одобрить (`Product.objects.filter(...).update(is_active=True)`, батч → `approved`) или отклонить (батч → `rejected`, `rejection_reason`, товары остаются `is_active=False` навсегда, не удаляются).
- **Точечное добавление одного товара** (`/seller/products/add/`) подтверждения администратора по-прежнему **не требует** — не путать, это разные пути, проверено отдельным тестом.
- Существующий простой CSV/.xlsx импорт в Django admin (`products/catalog_import.py`) **не тронут**, оставлен как есть.
- Ссылки в навигации (`templates/base.html`): «Импорт каталога» — для `user.can_manage_catalog` (продавец/админ), «Модерация импортов» — для `user.can_bulk_import_catalog` (только админ).
- Дубликат SKU при импорте — построчная ошибка (`ImportRow.error`), не роняет весь батч, остальные строки создаются — тот же принцип, что и в `products/catalog_import.py`.
- **Тесты** (`bulk_import/tests.py`, 15 штук) — upload/mapping/preview/дубликат SKU/блокировка отправки без картинок/одобрение/отклонение/изоляция между продавцами/права доступа (продавец не может попасть в модерацию и наоборот, аноним редиректится). Все 67 тестов проекта (52 старых + 15 новых) проходят, flake8/mypy чисты.
- **Подвох при написании теста на загрузку картинки**: вручную собранные байты PNG получились с невалидным CRC — Pillow (через `django.forms.ImageField.to_python` → `Image.verify()`) их отклонял, форма была невалидна, картинка молча не сохранялась (redirect всё равно происходил, ошибка нигде не показывалась). Чтобы такое не пропускать молча и в реальном использовании — добавил `messages.error(...)` в `batch_image_upload` на случай невалидной формы. Для тестовых картинок теперь генерирую настоящий PNG через `PIL.Image.new(...).save(buffer, 'PNG')`, а не через ручные байты.
- Не сделано (осознанно, не просили): собственная страница для повторной отправки отклонённого батча (продавцу придётся загружать файл заново); email-уведомление продавцу об одобрении/отклонении (заказы уведомляют по email, импорт — нет, можно добавить по аналогии с `orders/emails.py`, если понадобится).

## Переход на PostgreSQL везде, SQLite убран (2026-09-13, устарело — см. запись выше)

По просьбе пользователя SQLite-фолбэк в `config/settings.py` убран
полностью — **PostgreSQL теперь единственная поддерживаемая БД**, в т.ч.
для локальной разработки без Docker (раньше это был осознанный компромисс,
см. запись «Инфраструктура и локализация» ниже — он больше не действует).

- `DATABASES` в `config/settings.py` больше не ветвится по `POSTGRES_HOST` — всегда `django.db.backends.postgresql`, с `HOST` по умолчанию `localhost` (не `db` — это имя резолвится только внутри docker-сети, в контейнере `web` его по-прежнему переопределяет `docker-compose.yml`).
- `docker-compose.yml`: у сервиса `db` теперь `ports: ["5432:5432"]` — раньше порт наружу не публиковался (Postgres был доступен только контейнеру `web` через внутреннюю сеть). Публикация нужна, чтобы `manage.py runserver`/`pytest`, запущенные прямо на хосте (не в контейнере `web`), тоже могли подключиться — `docker compose up -d db` поднимает только Postgres, дальше Django на хосте работает как обычно.
- `.env.example`: `POSTGRES_HOST` по умолчанию теперь `localhost` (не `db`) — этот файл ориентирован в первую очередь на локальный (не-Docker) запуск; при запуске через docker-compose `POSTGRES_HOST=db` всё равно приходит из самого `docker-compose.yml`, а не из `.env`.
- **Локальной разработки на голом SQLite (без Postgres в каком-либо виде) больше нет** — если Postgres недоступен (ни Docker, ни локальная установка), `manage.py runserver`/`pytest`/`makemigrations` не заработают. Это осознанное решение, не забытый фолбэк.
- Проверено: `docker compose up -d db` + `manage.py migrate`/`pytest` с хоста (не из контейнера `web`) — миграции применяются к реальному Postgres, тесты проходят.

## Как дошли до этого стека (2026-08-24)

Проект был размазан по трём несинхронизированным местам:
1. **Этот репозиторий** — раньше содержал Laravel-скелет (2 коммита, включая случайно закоммиченную `vendor/`, 8244 файла). Полностью удалён и заменён на Django.
2. **Хостинг hoster.kz** (тот же провайдер, что у ecomeken.kz) — корень домена отдаёт 403 (заглушка с 2021 года), но по адресу `elektronik.kz/wordpress/` был рабочий демо-магазин на WordPress/WooCommerce с каталогом из 7 товаров. **Решение: отказаться от WordPress**, эта ветка больше не развивается.
3. **Google Drive**, папка `elektronik-kz` — содержит то, что в git не попало:
   - прайс-листы поставщиков (**FDCOM/Acer, Marvel**) — активно обновляются, это реальный источник товарного ассортимента, ещё не подключён к проекту;
   - файл учёта остатков;
   - старый `.env.example` с продакшн-конфигом (`APP_URL=https://elektronik.kz`, MySQL) — актуален только по домену/окружению, не по стеку (там был Laravel).

Итог: Python/Django выбран сознательно, чтобы не распыляться на два стека и не тратить время на PHP, который пользователь не использует в других проектах.

## Роли: продавец и администратор (2026-09-06)

- `accounts.User.role` (customer/seller/admin, default customer) — явное поле, не завязано на `is_staff`/`is_superuser`. Хелперы `User.can_manage_catalog` (seller/admin/superuser) и `User.can_bulk_import_catalog` (admin/superuser) — использовать их для проверок доступа, а не сравнивать `role` напрямую по всему коду.
- **Важный нюанс**: `User.save()` автоматически ставит `is_staff=True`, когда `role=ADMIN` — иначе администратор не сможет зайти в `/admin/` (Django admin требует `is_staff` независимо от нашего поля `role`). `role=SELLER` НЕ даёт `is_staff` — продавец работает только через кастомный UI, в Django admin ему хода нет.
- **Продавец** — карточки товаров через кастомный UI на самом сайте (не Django admin): `/seller/products/` (список), `/seller/products/add/`, `/seller/products/<pk>/edit/` (`shop/seller_views.py`, декоратор `seller_required`). Каталог общий — продавец может редактировать любой товар, привязки "мои товары" нет (осознанное решение, не многовендорная модель).
- **Администратор** — массовая загрузка каталога файлом (CSV/.xlsx) прямо в Django admin: кнопка "Импортировать каталог" на `/admin/shop/product/` → `/admin/shop/product/import-catalog/` (`shop/admin.py:ProductAdmin.import_catalog_view`, парсинг в `shop/catalog_import.py`).
