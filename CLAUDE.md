# elektronik.kz — контекст для Claude Code

Интернет-магазин электроники (ТОО/ИП пользователя, направление среди нескольких параллельных бизнес-инициатив). Читай этот файл в начале любой новой сессии в этом репозитории — ниже сжатая история решений, которые не видны из одного только кода.

## Реструктуризация приложений под названия команды (2026-09-13)

Группа делает параллельный курсовой проект с тем же наставником, но с другим
названием магазина и на другом стеке (структура другая, PostgreSQL) —
репозиторий `tamirlan1919/hop_django`. По просьбе пользователя **названия
приложений синхронизированы с их проектом**, чтобы сравнение/ревью между
проектами было проще: `products`, `payments`, `reviews`, `users` теперь
совпадают. **Код группы не копировался** — у них на момент сверки (коммит
`f09f1820`) только самые ранние заготовки моделей без API/JWT/ролей/i18n,
наш проект гораздо дальше продвинут; взяты только имена и границы
приложений, вся текущая логика — своя.

Что изменилось:
- `shop` → `products` (Product/Category/Brand, каталог, seller_views, catalog_import — без изменений в логике)
- `accounts` → `users` (User/Address, вход по email/телефону — без изменений в логике); URL-префикс `/accounts/...` → `/users/...`
- **`reviews` — новое отдельное приложение**, `Review` вынесена из `shop.models` (была `shop.Review`) в `reviews.models.Review` с `ForeignKey('products.Product', ...)`; вьюха `add_review`, форма, сериализатор и admin переехали вместе с моделью. URL `reviews:add_review` подключён в `config/urls.py` в корне (`path('', include('reviews.urls'))`), рядом с `products.urls`.
- **`payments` — новое отдельное приложение**. Раньше способ/факт оплаты был двумя полями прямо на `Order` (`payment_method`, и `status=PAID` выставлялся в `orders/services.py`). Теперь `Order` эти поля не хранит — есть `payments.Payment` (`OneToOneField` на `Order`, `method`, `status`, `paid_at`), создаётся сразу после создания заказа через `payments.services.create_payment(order, method)`; для карты сразу проставляет `Payment.status=PAID` и `Order.status=PAID` (мок, как и раньше). `CheckoutForm.payment_method` и `OrderCreateSerializer.payment_method` — теперь explicit-поля (не из модели `Order`), см. пример ниже.
- `AUTH_USER_MODEL = 'users.User'`, `LOGIN_URL='users:login'`, `LOGOUT_REDIRECT_URL='products:home'` и т.д. — обновлены везде в `config/settings.py`/`config/urls.py`.
- **Django ModelForm/ModelSerializer с полем, которого нет в модели**: `CheckoutForm.payment_method = forms.ChoiceField(...)` и `OrderCreateSerializer.payment_method = serializers.ChoiceField(...)` — рабочий паттерн: если имя явно объявлено как атрибут класса формы/сериализатора, его можно перечислять в `Meta.fields`, даже если у `Order` такого поля больше нет (объявленное поле просто переопределяет автогенерацию из модели). Не «баг», если увидишь это снова.
- **Миграции и dev-БД пересобраны с нуля** (как и в истории с `AUTH_USER_MODEL` 2026-08-25) — старые `0001_initial.py`/`0002_*.py` в `shop`(→`products`)/`accounts`(→`users`)/`cart`/`orders` удалены, `db.sqlite3` пересоздан, `manage.py makemigrations` прогнан заново. Тестовые аккаунты `admin@example.com`/`admin` и `seller@elektronik.kz` (роль seller) созданы заново в SQLite; **тестовые данные из предыдущих сессий (products id=1/2 и т.п.) потеряны** — это ожидаемо, не продакшен.
- Проверено после реструктуризации: `manage.py check` чистый, все 52 теста (`pytest`) проходят, `flake8`/`mypy` чистые, dev-сервер поднимается и отдаёт 200 на `/`, `/product/<slug>/`, `/cart/`, `/kk/`, `/api/docs/`, `/api/products/`.
- Если ещё раз понадобится сверяться с проектом группы — их репозиторий на GitHub, `tamirlan1919/hop_django`; сверялись по коммиту `f09f1820d4477d6bd990ae453ed441e7b07e123f`.

## Авторизация и личный кабинет (2026-08-25)

- Кастомная модель `accounts.User` (`AUTH_USER_MODEL`) — вход по **email или телефону**, без `username`. Телефон в формате `+7XXXXXXXXXX`, валидируется regex в `accounts/models.py`.
- Единое поле логина "email или телефон" (`accounts/forms.py: LoginForm`), формат определяется автоматически (`@` → email). Бэкенд аутентификации — `accounts.backends.EmailOrPhoneBackend`.
- **SMS/OTP-верификация телефона осознанно не делалась** — пока просто пароль. Если понадобится, это отдельная задача с выбором SMS-провайдера (для КZ, например Mobizon/SMSC).
- `accounts.Address` — адреса доставки пользователя, один может быть помечен `is_default`; используется для автозаполнения формы заказа.
- Корзина (`cart.Cart`/`CartItem`) — гостевая на сессии (`session_key`) для неавторизованных, привязывается к `user` после логина; слияние гостевой корзины в пользовательскую — сигнал `user_logged_in` в `cart/signals.py`.
- Заказ (`orders.Order`/`OrderItem`) — оформляется только авторизованным пользователем (`checkout` требует логин); при оформлении сохраняется снимок цены/названия товара (`price`, `product_name` в `OrderItem`), а не ссылка на текущую цену.
- Важный нюанс: `AUTH_USER_MODEL` подключали, когда БД уже существовала с дефолтным `auth.User` — пришлось снести `db.sqlite3` и миграции (в базе был только тестовый `admin`, реальных данных не было). Если ещё раз понадобится менять модель User — снова потребуется чистая пересборка миграций, это нельзя сделать data-migration'ом задним числом без боли.
- Тестовый суперпользователь для dev: `admin@example.com` / `admin` — только для локальной разработки, не для продакшена.

## Как дошли до этого стека (2026-08-24)

Проект был размазан по трём несинхронизированным местам:
1. **Этот репозиторий** — раньше содержал Laravel-скелет (2 коммита, включая случайно закоммиченную `vendor/`, 8244 файла). Полностью удалён и заменён на Django.
2. **Хостинг hoster.kz** (тот же провайдер, что у ecomeken.kz) — корень домена отдаёт 403 (заглушка с 2021 года), но по адресу `elektronik.kz/wordpress/` был рабочий демо-магазин на WordPress/WooCommerce с каталогом из 7 товаров. **Решение: отказаться от WordPress**, эта ветка больше не развивается.
3. **Google Drive**, папка `elektronik-kz` — содержит то, что в git не попало:
   - прайс-листы поставщиков (**FDCOM/Acer, Marvel**) — активно обновляются, это реальный источник товарного ассортимента, ещё не подключён к проекту;
   - файл учёта остатков;
   - старый `.env.example` с продакшн-конфигом (`APP_URL=https://elektronik.kz`, MySQL) — актуален только по домену/окружению, не по стеку (там был Laravel).

Итог: Python/Django выбран сознательно, чтобы не распыляться на два стека и не тратить время на PHP, который пользователь не использует в других проектах.

## Роли: продавец и администратор (2026-09-06)

- `accounts.User.role` (customer/seller/admin, default customer) — явное поле, не завязано на `is_staff`/`is_superuser`. Хелперы `User.can_manage_catalog` (seller/admin/superuser) и `User.can_bulk_import_catalog` (admin/superuser) — использовать их для проверок доступа, а не сравнивать `role` напрямую по всему коду.
- **Важный нюанс**: `User.save()` автоматически ставит `is_staff=True`, когда `role=ADMIN` — иначе администратор не сможет зайти в `/admin/` (Django admin требует `is_staff` независимо от нашего поля `role`). `role=SELLER` НЕ даёт `is_staff` — продавец работает только через кастомный UI, в Django admin ему хода нет.
- **Продавец** — карточки товаров через кастомный UI на самом сайте (не Django admin): `/seller/products/` (список), `/seller/products/add/`, `/seller/products/<pk>/edit/` (`shop/seller_views.py`, декоратор `seller_required`). Каталог общий — продавец может редактировать любой товар, привязки "мои товары" нет (осознанное решение, не многовендорная модель).
- **Администратор** — массовая загрузка каталога файлом (CSV/.xlsx) прямо в Django admin: кнопка "Импортировать каталог" на `/admin/shop/product/` → `/admin/shop/product/import-catalog/` (`shop/admin.py:ProductAdmin.import_catalog_view`, парсинг в `shop/catalog_import.py`). Upsert по `sku` (обновляет существующий товар, а не дублирует) — важно, т.к. прайс-листы поставщиков переобновляются периодически. Category/Brand создаются автоматически по названию из файла, если их ещё нет. Ошибки построчные (не роняют весь импорт), первые 20 показываются как admin messages.
